# 学管师工作台全栈开发规则

- 状态：已确认
- 负责人：总指挥
- 创建日期：2026-09-05
- 最后更新日期：2026-09-05
- 关联需求：所有真实全栈实现任务

> 本文档在项目进入真实后端、数据库、鉴权与联调阶段后生效。与已确认 PRD 或设计文档冲突时，必须暂停并由总指挥确认，禁止自行猜测业务规则。

## 一、开发顺序与范围

1. 先确认 PRD、数据模型和验收标准，再实现真实功能。
2. 按可验证的业务闭环垂直开发：迁移 → API → 前端接入 → 自测。禁止先铺完所有表、所有接口或所有页面再集成。
3. 现有前端原型是页面结构和交互的基准。接入真实后端时，只替换 mock service；禁止在页面中散落请求、mock 数据或业务判断。
4. 不实现未确认的业务能力，尤其是自动派发、提醒、任务系列、权限、删除和审计策略。
5. Redis 仅用于有明确收益的缓存、分布式锁、队列或限流；禁止预先引入无实际用途的缓存或队列。

## 二、六级实现阶梯

每次新增代码前，按优先级依次判断：

1. 这个能力是否真的需要存在？不需要则跳过。
2. Nuxt、Vue、Node.js、MySQL 或 Redis 原生能力是否足够？
3. 当前项目已有依赖、组件、composable、service 或工具函数能否复用？
4. 能否以清晰的最少代码实现？
5. 只有以上都不满足时，才新增依赖、抽象或复杂设计。

新增依赖必须说明用途、替代方案和影响范围。

## 三、目录与职责

1. API 使用 `server/api/{领域}/{动作}.{方法}.ts` 命名，例如 `server/api/students/list.get.ts`。
2. 鉴权、请求上下文和全局拦截放在 `server/middleware/`。
3. MySQL 连接池、查询和事务工具放在 `server/db/`；不得在 API 文件中创建连接池。
4. Redis 按用途封装在 `server/cache/` 或 `server/queue/`。
5. `composables/use*.ts` 只放 Vue 响应式状态、页面交互和业务编排。
6. `utils/` 只放纯函数或无 Vue 依赖的库封装；禁止在其中使用 `ref`、`reactive`、`computed`、`useState`、`useFetch`。
7. 页面和组件不得直接访问 mock 数据、数据库或 Redis；统一经过 composable、service 或 API 边界。
8. 同一模板或逻辑在两处以上复用时，必须抽为共享组件或函数。

## 四、组件与前端交互

1. 组件只负责一个 UI 区域或一个交互流程，不同时承担复杂数据获取、业务判断和展示职责。
2. 禁止组件内直接修改 `prop`；使用 `emit` 或 `defineModel`。
3. 可增删、排序或分页的数据列表必须使用稳定业务 ID 作为 `:key`。
4. 所有异步请求必须具备 loading、empty、error 三种状态。
5. 提交类按钮在请求期间必须禁用，避免重复提交。
6. 所有真实数据写操作必须有明确的成功和失败反馈。
7. 不得为接入后端而破坏已确认原型交互；若必须调整，先更新 PRD 和验收标准。

## 五、接口与类型

1. API 响应统一为 `{ status, msg, data }`。
2. 请求参数、响应 DTO 和领域类型必须明确；组件和 composable 禁止使用 `any`。
3. 不确定的外部输入使用 `unknown`，经类型守卫或 schema 校验后再使用。
4. API 不得直接返回数据库完整行、密码字段、内部错误堆栈或敏感信息。
5. 分页接口必须返回列表、总数、当前页和页大小，并限制最大页大小。
6. 禁止无 `LIMIT` 的列表查询。

## 六、安全与数据完整性

1. 所有 SQL 必须参数化，禁止拼接用户输入生成 SQL。
2. 所有写接口必须在服务端校验输入；前端校验只用于体验，不能作为可信校验。
3. 密码、数据库连接串、Redis 地址、JWT 密钥等只能存在于 `.env`，不得写入代码、文档、测试样例或 Git。
4. 学生、监护人联系方式等敏感信息必须按角色最小化返回和展示。
5. 删除、批量操作、合同作废、风险解除等重要操作，必须先在 PRD 定义权限、审计和可恢复策略。
6. 涉及多表写入时必须使用事务；成功或失败后必须释放连接。
7. 禁止 N+1 查询；列表关联数据优先使用合理的 JOIN、批量查询或聚合。

## 七、状态、缓存与并发

1. 业务状态必须有明确状态机和允许的流转，禁止由前端任意写入状态字符串。
2. Redis 缓存必须定义键名、TTL、失效策略和数据一致性责任方。
3. Redis 不可用时，核心读写业务必须有可预期行为，不得静默返回错误数据。
4. 任务完成、合同状态变更、风险处理等并发敏感写操作，必须在设计文档说明幂等和冲突处理策略。

## 八、数据库与迁移

1. 所有表结构、索引和初始字典数据必须通过 `database/migrations/` 管理。
2. 每次迁移必须可追踪，并提供回滚方案或明确不可逆原因。
3. 外键、唯一约束、非空约束和索引必须服务于已确认的业务规则，不做猜测性设计。
4. 核心业务数据的删除策略必须先确认，默认不做物理删除。

## 九、Git 与质量

1. 一个 commit 只做一件事；功能、修复、重构和文档更新不要混在同一个提交。
2. 只有用户明确要求“提交”或“commit”时才能创建 commit。
3. 禁止顺手格式化、改名、重排无关代码；每一行改动都必须对应当前任务。
4. 新代码替换旧实现时，旧代码、旧类型、旧 mock 分支和无效注释必须同步清理；除非存在明确 TODO、负责人和截止条件。
5. 每个功能闭环至少通过类型检查、Lint、相关单元测试和关键页面手工验证。

## 十、当前项目确认的业务边界

1. 任务采用“任务定义 + 任务分配”两层模型；不实现任务系列、自动顺延或自动派发。
2. 同一学生不得存在同一任务定义的多条未完成分配。
3. 学习记录允许编辑；删除和操作审计须在后续确认后实现。
4. 合同需有唯一编号；金额、支付、附件、续签、作废暂不进入当前实现范围。
5. 当前项目定位为内部工作台，保持现有 Nuxt 渲染策略；启用 SSR 前必须单独评估并经确认。
