## 5. 缺陷清单

### P2 — ATT-P2-01：同版本并发更新可能返回 503，而非承诺的 409 冲突

- 涉及文件：`server/db/attendance.ts:184-194`、`server/db/attendance.ts:262-275`、`server/utils/api.ts:50-70`。
- 复现条件：两名已登录用户（或两个窗口）几乎同时对同一既有出勤格提交相同 `expectedVersion` 但不同目标状态。两次事务都先以 `SELECT ... FOR SHARE` 读取同一行，随后都申请 `UPDATE` 所需的排他锁。
- 预期：其中一次更新成功；另一次稳定返回 `409 VERSION_CONFLICT`，界面按冲突提示保留选择并要求刷新核对。
- 实际：`FOR SHARE` 允许两个事务同时持有共享锁；两个事务随后升级为排他锁时，InnoDB 可选择其中一方为死锁受害者并抛出 `ER_LOCK_DEADLOCK`。该错误不是 `ApiError`，会被统一错误封装映射为 `503 STORAGE_UNAVAILABLE`，不是约定的 409。
- 影响：没有数据覆盖风险（事务会回滚），但高频并发编辑会得到误导性的服务故障提示，破坏版本冲突的确定性和前端冲突流程。
- 脱敏证据：当前更新读取使用 `FOR SHARE`，更新依赖 `id + version`；全局错误封装仅保留 `ApiError` 状态，其他数据库错误统一映射 503。本轮受无写入边界限制，没有在人库诱发并发死锁。
- 建议处理方向（仅供总指挥/开发）：改用避免共享锁升级死锁的原子乐观更新流程或独占锁读取，并将可预期的锁/版本竞争统一映射为 `VERSION_CONFLICT`；随后以两个受控会话做真实并发复验。

### P3 — ATT-P3-01：S10 自动化测试未覆盖数据访问层写入、冲突映射与审计原子性

- 涉及文件：`tests/unit/attendance.test.ts`、`server/db/attendance.ts`。
- 复现步骤：检查 S10 专项单测。该文件共 5 例，只调用规则解析、筛选/DTO 投影、迁移解析和审计实体数组；未以 mock connection 验证 `setAttendanceCell`、`ER_DUP_ENTRY → VERSION_CONFLICT`、旧版本、同状态重放、`UPDATE ... version`、审计写入或事务失败回滚。
- 预期：无法在人库写入时，至少以隔离 mock 覆盖出勤写入关键分支和 409/503 映射，防止回归。
- 实际：这些关键路径没有自动化用例；交付文档中“规则测试覆盖”的说法不能作为本轮对写入/审计路径的证据。

### 8.4 缺陷状态

#### ATT-P2-01 — 已关闭（代码与隔离回归测试）

原缺陷所依赖的 `FOR SHARE` 后更新锁升级路径已经删除。当前实现以单条带版本条件的原子更新决定胜负，在更新为零行后以当前读取区分“同状态重提”和“陈旧/并发更新”。本轮隔离竞争测试稳定得到一成功、一 `409 VERSION_CONFLICT`，未出现 503 映射。

真实 MySQL 多连接下的锁等待、隔离级别和最终 HTTP 响应仍为 **MANUAL**，因为本轮明确未创建出勤记录或使用登录会话。这是验证范围限制，不是仍开放的代码缺陷。

#### ATT-P3-01 — 已关闭

原有的 5 项专项测试已扩展为 11 项。现覆盖重复创建、旧版本、精确版本同状态无副作用、确定性同版本竞争、审计失败事务回滚，以及 409/no-store envelope。测试使用内存事务模拟，不读取配置或数据库，因此可重复且不触及真实业务数据。

未新增 P1、P2 或 P3 缺陷。

### 8.5 复验结论

1. **S10 的无数据 / 只读受控验收：通过（限定于源码、隔离内存事务测试、无会话 API 边界、类型检查和构建）。** ATT-P2-01 与 ATT-P3-01 在该范围内均已关闭。
